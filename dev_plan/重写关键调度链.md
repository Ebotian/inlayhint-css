重写关键调度链

目标: 用自然语言伪代码描述 clangd 的关键调度链，作为我们自己的 hinter 设计参考。

1. ClangdLSPServer::bindMethods

职责:
	// 在初始化阶段，把 LSP 方法名和处理函数绑定起来。
	// 它不处理具体业务，只建立“消息 -> handler”的路由表。

依赖:
	// 依赖 LSPBinder、ClientCapabilities、以及 ClangdLSPServer 上已经准备好的各个 onXXX 函数。

输入:
	// 输入一组能力信息 Caps，用来决定某些方法是否需要注册，或者注册哪种形式的入口。

输出:
	// 输出是一个已经填充好的 handler 映射表。
	// 之后 MessageHandler 收到请求时，会按这个表分发到对应函数。

伪代码:
	function bindMethods(Bind, Caps) {
		// 1. 依次注册通知、请求、命令。
		// 2. 每个注册项都把字符串方法名绑定到一个成员函数。
		// 3. 某些方法会根据能力开关决定是否注册。
		// 4. 同时注册 outgoing method / notification，供后续 handler 发送响应。
		register("initialized", onInitialized)
		register("shutdown", onShutdown)
		register("sync", onSync)

		register("textDocument/...", onDocumentXXX)
		register("workspace/...", onWorkspaceXXX)
		register("textDocument/inlayHint", onInlayHint)
		register("clangd/inlayHints", onClangdInlayHints)

		if (Caps.enableOutgoingCalls) {
			register("callHierarchy/outgoingCalls", onCallHierarchyOutgoingCalls)
		}

		setupOutgoing("workspace/applyEdit")
		setupOutgoing("textDocument/publishDiagnostics")
		setupOutgoing("window/showMessage")
	}

要点:
- 这里的核心动作不是计算，而是建立路由。
- 它把“方法名”变成“成员函数入口”，让后续的消息分发可以保持简单。
- 对我们自己的 hinter 来说，这一层如果存在，也应该只负责注册入口，不放 hint 生成逻辑。

2. ClangdLSPServer::onInlayHint

职责:
	// 接收标准 LSP 的 textDocument/inlayHint 请求。
	// 不自己生成 hint，只把请求转发到 ClangdServer::inlayHints。
	// 它是标准协议入口的薄适配层。

依赖:
	// 依赖 InlayHintsParams、Reply 回调，以及 Server->inlayHints。

输入:
	// 输入是一个已经解析好的 InlayHintsParams，里面包含文件 URI 和限制范围。

输出:
	// 输出不是直接的 JSON，而是把请求交给服务层后的 std::vector<InlayHint> 回调链。

伪代码:
	function onInlayHint(Params, Reply) {
	  // 1. 从 LSP 参数中取出文件路径和范围。
	  // 2. 直接调用服务层 inlayHints。
	  // 3. 把 Reply 原样传下去，等待服务层返回结果。
	  Server.inlayHints(Params.file, Params.range, Reply)
	}

要点:
- 这一层没有 AST 处理，也没有 hint 生成逻辑。
- 它只是把标准 LSP 入口接到服务层接口上。
- 这里的“适配”只发生在协议参数到服务调用的转换上。
- 对我们自己的 hinter 来说，如果只支持标准 LSP，这一层就是唯一的外部入口之一。

3. ClangdServer::inlayHints

职责:
	// 接收服务层的 inlay hint 请求。
	// 先保证目标文件的 AST 可用，再调用真正的 hint 生成函数。
	// 它不做协议序列化，只做“任务调度 + AST 获取 + 结果转发”。

依赖:
	// 依赖 WorkScheduler、InputsAndAST、ParsedAST、以及 clangd::inlayHints。

输入:
	// 输入是文件路径 File、可选的 RestrictRange、以及回调 CB。

输出:
	// 输出是一个 std::vector<InlayHint> 回调结果，或者 AST 获取失败时的错误。

伪代码:
	function inlayHints(File, RestrictRange, CB) {
	  // 1. 构造一个延迟执行的 Action。
	  // 2. 这个 Action 会等待调度器提供 InputsAndAST。
	  // 3. 如果拿 AST 失败，就直接把错误传给 CB。
	  // 4. 如果拿 AST 成功，就调用 clangd::inlayHints(AST, RestrictRange)。
	  Action = lambda(InpAST) {
	    if (!InpAST) {
	      CB(error)
	      return
	    }
	    CB(clangd.inlayHints(InpAST.AST, RestrictRange))
	  }

	  // 5. 把 Action 交给 WorkScheduler。
	  // 6. WorkScheduler 负责调度、等待 AST、处理并发与取消。
	  WorkScheduler.runWithAST("InlayHints", File, Action, Transient)
	}

要点:
- 这一层已经不再关心 LSP 协议名，只关心“文件 + AST + 结果回调”。
- 它是服务层封装，不是 hint 算法本身。
- 真正的核心依旧是 clangd::inlayHints(...)。
- 对我们自己的 hinter 来说，这一层是“服务调度层”的模板：先拿上下文，再进核心逻辑。

4. clangd::inlayHints / InlayHints.cpp 顶层函数

职责:
	// 接收已经准备好的 ParsedAST，生成当前文件可用的 inlay hints。
	// 这一层只负责顶层编排：开关检查、visitor 构造、AST 遍历、结果去重。
	// 真正的逐条规则判断交给 InlayHintVisitor。

依赖:
	// 依赖 Config::current()、ParsedAST、InlayHintVisitor、InlayHintOptions、以及结果容器。

输入:
	// 输入是一个可用的 ParsedAST，可选的 RestrictRange，以及控制 hint 行为的 HintOptions。

输出:
	// 输出是 std::vector<InlayHint>。
	// 如果 inlay hints 被配置关闭，则直接返回空结果。

伪代码:
	function inlayHints(AST, RestrictRange, HintOptions) {
	  // 1. 准备结果容器。
	  Results = []

	  // 2. 读取当前配置，如果 inlay hints 被关闭，直接返回空。
	  Cfg = Config.current()	
	  if (!Cfg.InlayHints.Enabled) {
	    return Results
	  }

	  // 3. 构造 visitor，把结果容器、AST、配置和参数一起交给它。
	  Visitor = InlayHintVisitor(Results, AST, Cfg, RestrictRange, HintOptions)

	  // 4. 让 visitor 遍历 AST，逐个节点收集 hint。
	  Visitor.TraverseAST(AST.getASTContext())

	  // 5. 对结果排序并去重，避免重复 instantiation 或重复访问造成重复 hint。
	  sort(Results)
	  unique(Results)

	  // 6. 返回最终结果。
	  return Results
	}

要点:
- 这一层已经接近“核心入口”，但仍然不是规则本身。
- 它的职责是把配置、AST 和 visitor 串起来，并把收集到的结果规范化。
- 这里最重要的信号是：真正的判断逻辑在 InlayHintVisitor 中，而不是顶层函数中。
- 对我们自己的 hinter 来说，这一层可以作为“核心入口包装器”的参考：先检查开关，再把上下文交给真正的规则执行器。

5. InlayHintVisitor 构造函数

职责:
	// 把顶层函数已经准备好的上下文一次性装进 visitor。
	// 它本身不生成任何 hint，只负责初始化后续遍历所需的状态。
	// 这一步的核心是“绑定资源”和“准备打印策略”。

依赖:
	// 依赖结果容器 Results、ParsedAST 提供的 ASTContext / TokenBuffer / SourceManager、Config、HeuristicResolver、PrintingPolicy、HintOptions。

输入:
	// 输入是外部传进来的 Results、ParsedAST、当前配置 Cfg、RestrictRange 和 HintOptions。

输出:
	// 输出是一个已经初始化好的 InlayHintVisitor 对象。
	// 构造过程同时会把主文件内容缓存到 MainFileBuf。

伪代码:
	constructor InlayHintVisitor(Results, AST, Cfg, RestrictRange, HintOptions) {
	  // 1. 保存对结果容器、AST、token buffer、配置和参数的引用/副本。
	  this.Results = Results
	  this.AST = AST.getASTContext()
	  this.Tokens = AST.getTokens()
	  this.Cfg = Cfg
	  this.RestrictRange = move(RestrictRange)
	  this.MainFileID = AST.getSourceManager().getMainFileID()
	  this.Resolver = AST.getHeuristicResolver()
	  this.TypeHintPolicy = AST.getPrintingPolicy()
	  this.HintOptions = HintOptions

	  // 2. 读取主文件的原始文本，后续很多“注释/行尾/范围”判断都要用它。
	  MainFileBuf = SourceManager.getBufferData(MainFileID)

	  // 3. 调整打印策略，让类型名更短、更适合做 hint。
	  TypeHintPolicy.SuppressScope = true
	  TypeHintPolicy.AnonymousTagNameStyle = Plain

	  // 4. 不强制使用 canonical type，以便 auto 相关的抑制规则还能生效。
	}

要点:
- 这个构造函数的重点不是“计算”，而是把后续遍历需要的所有上下文一次性固定下来。
- 它提前缓存主文件文本，是为了后面做注释匹配、范围检查、block end 判断。
- 它提前调整打印 policy，是为了控制 hint 的可读性和长度。
- 对我们自己的 hinter 来说，这一层说明：visitor 最好是“状态打包器”，而不是在遍历过程中到处临时取上下文。

6. RecursiveASTVisitor::TraverseAST / TraverseDecl

职责:
	// 把“开始遍历整棵 AST”这件事接起来。
	// TraverseAST 只是入口别名，真正工作是把 TranslationUnitDecl 交给 TraverseDecl。
	// TraverseDecl 再根据具体 Decl 类型分发到更具体的 TraverseXXXDecl。

依赖:
	// 依赖 ASTContext、TranslationUnitDecl、以及派生 visitor 对 TraverseDecl / TraverseXXXDecl 的重写。

输入:
	// 输入是一个 ASTContext，内部包含 TranslationUnitDecl 作为整棵 AST 的根。

输出:
	// 输出是一次深度优先遍历的启动结果。
	// 如果派生类在某个阶段返回 false，遍历会立即中止。

伪代码:
	function TraverseAST(AST) {
	  // 1. 找到翻译单元根节点。
	  TU = AST.getTranslationUnitDecl()

	  // 2. 直接把根节点交给 TraverseDecl。
	  return TraverseDecl(TU)
	}

	function TraverseDecl(Node) {
	  // 1. 如果节点为空，直接返回。
	  if (!Node) {
	    return true
	  }

	  // 2. 根据当前 Decl 的动态类型，跳到对应的 TraverseXXXDecl。
	  // 3. 每个 TraverseXXXDecl 负责自己的前置处理、子节点遍历和回调。
	  switch (Node.kind) {
	    case TranslationUnitDecl:
	      return TraverseTranslationUnitDecl(Node)
	    case FunctionDecl:
	      return TraverseFunctionDecl(Node)
	    case VarDecl:
	      return TraverseVarDecl(Node)
	    // ... 其他 Decl 类型
	  }
	}

要点:
- 这一步还是“框架层”，不是业务层。
- 它做的是从 AST 根开始，按照节点类型把控制权交给更具体的遍历函数。
- 对 InlayHintVisitor 来说，`Visitor.TraverseAST(AST.getASTContext())` 的真实含义就是：从整棵翻译单元开始，逐层走到各个会触发 `Visit*` 的节点。
- 对我们自己的 hinter 来说，这说明 visitor 的入口不该直接从某个叶子节点开始，而应该从 TU 级根入口启动，保持和 clangd 一样的完整遍历模型。

7. TranslationUnitDecl

职责:
	// 作为整棵 AST 的顶层声明上下文，承载翻译单元里的所有顶层 Decl。
	// 它是遍历的根节点，也是后续所有 Decl 遍历的起点。

依赖:
	// 依赖 ASTContext、DeclContext、Redeclarable 这几个基础结构。
	// 在遍历链上，它被 TraverseAST 选作根，然后交给 TraverseDecl 继续分发。

输入:
	// 输入是一个已经构建好的 ASTContext。
	// TranslationUnitDecl 内部保存这个 ASTContext，并把顶层声明挂到自己的 DeclContext 上。

输出:
	// 输出不是算法结果，而是一个可供遍历的 AST 根上下文。
	// 从这里可以继续遍历到 PragmaCommentDecl、NamespaceDecl、VarDecl、FunctionDecl 等顶层声明。

伪代码:
	class TranslationUnitDecl {
	  ASTContext &Ctx
	  NamespaceDecl *AnonymousNamespace

	  function getASTContext() {
	    return Ctx
	  }
	}

要点:
- 这个类本身不做 hint 计算，它只是 AST 的最顶层容器。
- `TraverseAST(AST)` 最终拿到的就是这个根节点，然后把它交给 `TraverseDecl`。
- 对我们自己的 hinter 来说，这说明“遍历入口”和“业务规则”之间还隔着一个统一的 AST 根上下文对象。

8. RecursiveASTVisitor::TraverseDecl

职责:
	// 接收一个 Decl 节点，先决定它值不值得继续看，再分发给更具体的 TraverseXXXDecl。
	// 这一层负责“过滤 + 动态类型分发”，但不负责具体规则判断。

依赖:
	// 依赖 shouldVisitImplicitCode()、Decl::isImplicit()、Decl 的动态类型，以及派生类提供的 TraverseXXXDecl。

输入:
	// 输入是一个 Decl*，它可能是 TranslationUnitDecl、FunctionDecl、VarDecl、NamespaceDecl 等任意声明节点。

输出:
	// 输出是对当前 Decl 的遍历结果。
	// 如果当前节点被过滤掉，或者派生类返回 false，遍历会提前结束。

伪代码:
	function TraverseDecl(D) {
	  // 1. 空节点直接跳过。
	  if (!D) {
	    return true
	  }

	  // 2. 如果默认不看隐式代码，就先过滤掉隐式 Decl。
	  if (!shouldVisitImplicitCode()) {
	    if (D.isImplicit()) {
	      // 2.1 某些特殊隐式节点仍要保留，例如模板类型参数的约束。
	      if (D is TemplateTypeParmDecl) {
	        return TraverseTemplateTypeParmDeclConstraints(D)
	      }
	      return true
	    }

	    // 2.2 某些合成的 deduction guide 也默认跳过。
	    if (D is FunctionTemplateDecl and is alias-template deduction guide) {
	      return true
	    }
	  }

	  // 3. 根据 Decl 的动态类型分发到更具体的 TraverseXXXDecl。
	  switch (D.kind) {
	    case TranslationUnit:
	      return TraverseTranslationUnitDecl(D)
	    case Namespace:
	      return TraverseNamespaceDecl(D)
	    case Var:
	      return TraverseVarDecl(D)
	    case Function:
	      return TraverseFunctionDecl(D)
	    // ... 其他 Decl 类型
	  }
	}

要点:
- 这一层仍然属于遍历框架，不是业务算法。
- 它的关键价值是“先筛掉不想看的节点，再把真正要看的节点交给更具体的处理函数”。
- 对我们自己的 hinter 来说，这一层说明：如果不想处理隐式节点，最好在统一入口做一次集中过滤，而不是让每个 hint 规则自己重复判断。
- 这里的分发也说明，真正的节点级逻辑应该放到 `Visit*` 或具体的 `TraverseXXXDecl` 里，而不是塞进统一入口。

9. AnalysisASTVisitor::TraverseBindingDecl

职责:
	// 这是一个针对 BindingDecl 的 traversal 补丁。
	// 它先补上 RecursiveASTVisitor 默认不会单独遍历的 holding variable，
	// 再把控制权交回给基类的 BindingDecl 遍历逻辑。
	// 它体现的是“框架默认路径不够时，在局部补一条边”。

依赖:
	// 依赖 BindingDecl::getHoldingVar()、TraverseDecl(HoldingVar)、以及 DynamicRecursiveASTVisitor::TraverseBindingDecl。
	// 还依赖 RecursiveASTVisitor 对 BindingDecl 的默认遍历行为。

输入:
	// 输入是一个 BindingDecl*，通常来自结构化绑定相关的 AST 节点。
	// 其中可能关联一个持有原始对象的 VarDecl。

输出:
	// 输出是对 BindingDecl 及其 holding variable 的完整遍历结果。
	// 如果 holding variable 存在，它会先被纳入遍历路径。

伪代码:
	function TraverseBindingDecl(BD) {
	  // 1. 先补上框架默认不会走到的 holding variable。
	  if (BD has HoldingVar) {
	    TraverseDecl(BD.getHoldingVar())
	  }

	  // 2. 再交给基类处理 BindingDecl 自己的遍历。
	  return Base.TraverseBindingDecl(BD)
	}

要点:
- 这类函数不是主算法核心，但很有设计价值，因为它展示了“在不改框架的前提下修补遍历覆盖面”的做法。
- 它说明某些 AST 节点的语义并不只在自身，还关联到额外的辅助声明，遍历时需要主动补一条边。
- 对我们自己的 hinter 来说，这种模式提醒我们：如果一个节点的语义依赖旁边的附属节点，就不要只看框架默认遍历，要检查是否需要手动扩展路径。

10. 和 LexicallyOrderedRecursiveASTVisitor 的区分

职责:
	// 这一类 visitor 不是在补“漏掉的语义节点”，而是在修正“遍历顺序”。
	// 它的目标是让遍历结果更接近源码书写顺序，尤其是在 AST 物理结构和源码顺序不一致时。

依赖:
	// 依赖 SourceManager、DeclContext 中的 sibling 关系、以及节点的源位置比较。
	// 还依赖 BaseType::TraverseDecl / TraverseObjCImplementationDecl 先完成基础遍历。

输入:
	// 输入是一个已经存在于 AST 中的声明节点，以及对应的源码位置信息。
	// 在 Objective-C implementation / category implementation 场景下，还会有随后出现但语义上属于该块的 sibling decl。

输出:
	// 输出是更接近词法顺序的遍历结果。
	// 它不增加新的语义边，只改变“什么时候遍历到这些节点”。

区分点:
- `AnalysisASTVisitor::TraverseBindingDecl` 属于“补遍历覆盖面”：框架默认没走到的关联节点，需要手动补进去。
- `LexicallyOrderedRecursiveASTVisitor::TraverseObjCImplementationDecl` 属于“补遍历顺序”：节点本来会被遍历，但需要延后到更符合源码词法顺序的时候再遍历。
- 前者关心的是“有没有被遍历到”，后者关心的是“以什么顺序被遍历到”。
- 前者是在语义完整性上补洞，后者是在结果排序上做修正。

要点:
- 这两类 override 都是在改框架默认行为，但改的目标不同。
- 如果在学习笔记里混在一起，很容易误以为它们都属于“业务逻辑核心”，其实不是。
- 对我们自己的 hinter 来说，先问清楚需求是“补节点”还是“调顺序”，可以直接决定该写 Traverse override 还是排序/收集策略。

11. TraverseRecordDecl 的“先收集，后整理”模式

职责:
	// 这一类 override 先让基类完成正常遍历和收集，再在遍历结束后对结果做清理或修正。
	// 它不是补路径，也不是调顺序，而是“先收，再删 / 合并 / 纠偏”。

依赖:
	// 依赖 Base::TraverseRecordDecl(Decl) 先把 record 的主遍历跑完。
	// 还依赖 APISet 和 USR 之类的结果容器，方便在后处理阶段移除不该保留的记录。

输入:
	// 输入是一个 RecordDecl*，通常可能是匿名 struct / union。
	// 其中有些 record 在语义上只是中间产物，不一定应该直接留在最终 API 集合里。

输出:
	// 输出是一次“遍历完成 + 结果校正”后的记录状态。
	// 如果记录不符合保留条件，后处理阶段会把它从 API 中移除。

伪代码:
	function TraverseRecordDecl(Decl) {
	  // 1. 先按基类规则完成遍历和收集。
	  Ret = Base.TraverseRecordDecl(Decl)

	  // 2. 遍历结束后，检查这个 record 是否属于应保留的结果。
	  if (Decl is anonymous struct/union and not embedded in var declarator) {
	    API.removeRecord(USR(Decl))
	  }

	  // 3. 返回基类遍历的结果，保持遍历控制流一致。
	  return Ret
	}

要点:
- 这类函数的重点不是 traversal 本身，而是 traversal 结束后的结果整理。
- 它和 `TraverseBindingDecl` 的区别在于：`TraverseBindingDecl` 是补一条遍历边，这里是改最终结果集合。
- 它和 `LexicallyOrderedRecursiveASTVisitor` 的区别在于：后者改顺序，这里改保留策略。
- 对我们自己的 hinter 来说，这一类模式非常像“先收集候选 hint，再统一过滤/去重/删除”。
- 你现在学到的是：有些 visitor 的 `TraverseXXX` 并不是主规则入口，而是一个收尾钩子，用来保证最终输出干净。

12. 阶段性整理

已经确认的模式:
- 统一入口层负责调度，不负责业务细节。
- 一部分 override 是在补遍历覆盖面，比如 `TraverseBindingDecl`。
- 一部分 override 是在调遍历顺序，比如 `LexicallyOrderedRecursiveASTVisitor`。
- 一部分 override 是在做遍历后清理，比如 `TraverseRecordDecl` / `TraverseCXXRecordDecl`。
- `TraverseFunctionHelper` 代表一类“公共遍历配方”，把函数相关的共同步骤集中在一起。
- `RecursiveASTVisitor` 的 `DEF_TRAVERSE_DECL` / `DEF_TRAVERSE_TYPE` / `DEF_TRAVERSE_TYPELOC` 说明：大量节点是按“框架模板 + 少量特化”组织的。

对我们自己的 CSS hinter 的直接启发:
- 先做一个稳定的顶层入口，负责拿上下文、配置和范围。
- 规则采集和规则筛选要分离，最好先收集候选，再统一整理。
- 对特殊节点保留少量局部补丁入口，不要把所有边界情况塞进主流程。
- 结果层应该有统一的去重、排序和清理策略。

13. 接下来的读源码方向

优先顺序:
1. 继续看 `TraverseFunctionHelper` 之后最关键的业务节点：`VisitCallExpr`、`VisitTypeLoc`、`VisitVarDecl` 这一类真正产出结果的函数。
2. 回到 `InlayHints.cpp`，对照它的 `InlayHintVisitor` 具体看它是怎样把“收集候选 -> 过滤 -> 去重 -> 输出”串起来的。

职责:

	// 它负责把各种 call 形式归一到一个统一的 Callee 语义，再交给 `processCall`。

依赖:
	// 依赖 `Config::InlayHints.Parameters`、`HeuristicResolver`、`getFunctionProtoTypeLoc`、以及 `Callee` 这个归一化载体。

输入:
	// 输入是一个 `CallExpr*`，可能来自普通函数调用、成员函数调用、函数对象调用、或者函数指针调用。

	// 输出不是 hint 本身，而是对调用点的筛选结果；满足条件时，调用会被转换成统一的 `Callee + Args` 形式，交给 `processCall`。

	function VisitCallExpr(E) {
	  if parameters hint disabled:
	    return
	  if call form is not suitable:
	    return
	  if resolver cannot resolve to exactly one callee:

	  Args = normalize arguments, including dropping implicit object argument when needed

16. 对 CSS hinter 的通用启发

职责:

依赖:
	// 依赖统一入口、语义归一、候选筛选、结果落点、去重和排序。
	// 也依赖一条明确的“来源 -> 转发/覆盖 -> 最终展示”链路。

输入:
	// 输入是 CSS 里的候选信息：属性值、变量引用、层叠结果、覆盖关系、默认 fallback、以及用户已经显式写出的内容。

输出:
	// 输出是最终要显示给用户的 hint 文本，以及它应该挂到源码中的位置。

伪代码:
	function buildCssHint(candidate) {
	  origin = resolveOrigin(candidate)
	  semantic = followForwardingOrOverrideChain(origin)
	  if shouldSuppress(semantic):
	    return
	  text = chooseBestDisplayText(semantic)
	  range = computeHintRange(candidate)

要点:

17. processCall 的核心总结

职责:
	// 这一层才是真正把一次调用转换成可显示 inlay hint 的地方。
	// 它接收已经归一化好的 Callee 和 Args，负责产出参数名提示、引用提示和默认参数提示。
	// 可以把它理解成“调用语义 -> 提示文本”的核心加工厂。

依赖:
	// 依赖上游 `VisitCallExpr` / `VisitCXXConstructExpr` 传下来的统一调用表示。
	// 依赖 `chooseParameterNames`、`shouldHintName`、`shouldHintReference`、`isSetter`、`isSimpleBuiltin`、`joinAndTruncate`、`addInlayHint`。
	// 还依赖 `Lexer::getSourceText`、`getDefaultArgRange`、`resolveForwardingParameters` 这些用来补足语义和重建源码文本的辅助接口。

输入:
	// 输入是一个已经解析好的 `Callee`、括号或大括号位置 `RParenOrBraceLoc`，以及归一化后的实参列表 `Args`。
	// 其中 `Callee` 可能来自真实函数声明，也可能来自函数类型位置；`Args` 可能已经去掉了隐式对象参数。

输出:
	// 输出是一组最终写入 `Results` 的 `InlayHint`。
	// 这些 hint 可能是参数名 hint，也可能是默认参数 hint；如果条件不满足，则什么都不输出。

伪代码:
	function processCall(Callee, RParenOrBraceLoc, Args) {
	  // 1. 先做最小前置过滤：配置关闭、无参数、复制/移动构造等场景直接返回。
	  if no parameter-related feature enabled or Args.empty():
	    return
	  if Callee is copy/move constructor:
	    return

	  // 2. 统一参数来源，并把显式对象参数、转发参数包等做归一化。
	  Params = normalized parameters of Callee
	  ForwardedParams = normalized forwarded parameters of Callee

	  // 3. 选择真正适合展示的参数名。
	  ParameterNames = chooseParameterNames(ForwardedParams)

	  // 4. 排除 setter / 简单 builtin 等低价值调用。
	  if Callee is setter or simple builtin:
	    return

	  // 5. 逐个参数检查：
	  //    - 是否应该显示名字
	  //    - 是否应该加 &
	  //    - 当前实参是否是默认实参
	  for each i:
	    if Args[i] is pack expansion:
	      break
	    if Args[i] is default arg:
	      collect abbreviated default text
	    else if name/reference hint should be shown:
	      add parameter hint at Args[i]

	  // 6. 如果收集到了默认参数，统一拼接并挂到调用结束位置。
	  if there are default args:
	    add default-argument hint at RParenOrBraceLoc
	}

要点:
- 这一步已经进入“真正产出结果”的层面，不再只是调度或归一化。
- 它的核心任务不是判断调用能不能进来，而是判断“每个参数该显示什么信息、显示到哪里”。
- 它把参数名提示和默认参数提示放在同一个函数里，但通过不同分支分别处理，说明 clangd 的设计是“同一调用点，多种 hint 并行生成”。
- 对我们自己的 CSS hinter 来说，这一层可以直接类比成“候选项已经收集好之后，真正把候选项变成最终显示文本”的阶段。
- 对我们自己的 hinter 来说，这类函数应当尽量薄，只做输入筛选、语义整理和转发。

18. 输出层的共同模式

职责:
	// 这一层负责把“已经决定要显示的语义结果”安全地放到编辑器里。
	// 它不再判断语义本身，而是判断位置是否有效、范围是否可见、类别是否允许、以及最终文本该怎么拼。

依赖:
	// 依赖 `getHintRange`、`addInlayHint`、`addTypeHint`、`addDesignatorHint`、`addBlockEndHint`、`computeBlockEndHintRange`、`shouldPrintTypeHint`、`maybeDesugar`。
	// 还依赖 `Tokens`、`SourceManager`、`MainFileBuf`、`HintOptions` 和 `Cfg.InlayHints` 这些用来做范围与展示控制的上下文。

输入:
	// 输入通常是一个语义上的 SourceRange 或者一个已经准备好的显示文本。
	// 对类型提示和 block end 提示来说，还会额外输入类型信息、括号位置、声明名和可选标点。

输出:
	// 输出是最终进入 `Results` 的 `InlayHint`。
	// 如果范围不合法、位置不在主文件、或者内容过长，函数会直接放弃输出。

伪代码:
	function emitHint(payload) {
	  range = resolveVisibleRange(payload.sourceRange)
	  if not valid(range):
	    return
	  if not allowedByConfig(payload.kind):
	    return
	  if payload.needsNormalization:
	    payload = normalize(payload)
	  results.push(makeHint(range, payload))
	}

要点:
- `getHintRange` 负责把语义范围过滤成“主文件中可见、可定位”的范围。
- `addInlayHint` 是总入口，负责统一做配置检查、左右侧定位和结果写入。
- `addTypeHint` 是类型类 hint 的专用出口，先做去糖和长度控制，再交给 `addInlayHint`。
- `addBlockEndHint` 是块尾类 hint 的专用出口，先计算 `{}` 或 `};` 这样的精确落点，再控制 label 长度。
- 这一层和上面的 `processCall` 形成清晰分工：前者负责“什么值得提示”，后者负责“怎么把提示送到界面上”。

20. CSS 左右侧 hint 与 C++ 的共性

职责:
	// 这一层不是在比较两个语言的具体语法，而是在抽象它们共同的“认知布局”原则。
	// 左右侧 hint 的本质，是把“解释信息”和“结果信息”放在最适合阅读的位置。

依赖:
	// 依赖语义识别、范围落点、去噪判断、以及 hint 类型和显示侧的统一约束。
	// 在 C++ 中，这些约束体现为参数名、designator、类型、块尾提示等不同类别；在 CSS 中，则会对应 shorthand、层叠、继承、覆盖和默认值等语义链。

输入:
	// 输入是一个可推导的语义对象，以及它在源码中的候选位置。
	// 这个对象可能是参数、表达式、初始化项，也可能是 CSS 的属性值、分量、变量引用或层叠结果。

输出:
	// 输出是一个左侧或右侧的 hint，外加它应该如何与源码主体协同呈现。
	// 左侧偏向“先解释再读取”，右侧偏向“先读取再补充”。

伪代码:
	function placeHint(semantic) {
	  if semantic is role-label:
	    attach to left
	  else if semantic is result-summary:
	    attach to right
	  if source already expresses same info:
	    suppress hint
	}

要点:
- 左侧 hint 更适合“角色标签”，例如 C++ 参数名、designator，CSS 中也适合 shorthand 分量名、来源名、方向名。
- 右侧 hint 更适合“结果补充”，例如 C++ 类型、块尾注释，CSS 中也适合最终值、展开结果、层叠后归宿。
- 两边都要先判断信息是否已经在源码里显式存在，避免重复提示。
- 两边都必须有稳定、精确的落点，否则再正确的语义也会变成噪音。
- 对 CSS hinter 来说，这个共性说明：左右侧不是 UI 细节，而是语义分工，应该先从“它代表什么角色”与“它最终成为什么结果”两个维度来设计。

21. addBlockEndHint 的分析

职责:
	// 这一层是块尾提示的专用输出包装器。
	// 它不负责判断“这个块是否有意义”，而是接收已经确定要显示的块尾语义，把它拼成最终可写入的 hint。

依赖:
	// 依赖 `computeBlockEndHintRange` 先判断块尾是否有合法落点。
	// 依赖 `addInlayHint` 作为统一的结果写入入口。
	// 还依赖 `HintSide::Right`、`InlayHintKind::BlockEnd`、`HintOptions.HintMinLineLimit` 的间接控制，以及调用者提供的 `DeclPrefix`、`Name`、`OptionalPunctuation`。

输入:
	// 输入是一个块范围 `BraceRange`，一个声明前缀 `DeclPrefix`，一个名字 `Name`，以及一个可选尾随标点 `OptionalPunctuation`。
	// 这些输入分别表示“这是什么结构”“它叫什么”“块尾后面可能还有什么符号”。

输出:
	// 输出是一个最终写入 `Results` 的块尾 InlayHint。
	// 如果落点不合法、label 太长，或者范围计算失败，就直接不输出。

伪代码:
	function addBlockEndHint(BraceRange, DeclPrefix, Name, OptionalPunctuation) {
	  HintRange = computeBlockEndHintRange(BraceRange, OptionalPunctuation)
	  if HintRange is invalid:
	    return

	  Label = DeclPrefix
	  if Label and Name are both non-empty:
	    Label += " "
	  Label += Name

	  if Label too long:
	    return

	  addInlayHint(HintRange, Right, BlockEnd, " // ", Label, "")
	}

要点:
- 它的第一步不是拼文本，而是先依赖 `computeBlockEndHintRange` 判断这个块尾是否真的能显示。
- 它把块尾提示统一做成注释样式，前缀固定是 ` // `，这让提示在视觉上自然地附着在源码末尾。
- 它会把声明类别和名字组合成短 label，但 label 过长时宁可不显示，说明可读性优先于完整性。
- 它把“块尾语义的构造”和“最终 hint 写入”分开，自己只负责包装，不负责底层位置合法性。
- 对 CSS hinter 来说，这种结构适合块级语义提示：先算可落点，再拼展示文本，最后交给统一输出入口。

22. computeBlockEndHintRange 的分析

职责:
	// 这一层是块尾 hint 的真正落点判定器。
	// 它不生成文本，也不决定显示什么内容，只回答一个问题：这段块尾能不能安全、精确地挂上 hint。

依赖:
	// 依赖 `AST.getSourceManager()`、`MainFileID`、`MainFileBuf`、`HintOptions.HintMinLineLimit`。
	// 还依赖 token / 源文件位置、尾随标点约束，以及 `computeBlockEndHintRange` 外围的主文件文本缓存。

输入:
	// 输入是一个块的括号范围 `BraceRange`，以及一个可选尾随标点 `OptionalPunctuation`。
	// `BraceRange` 表示整个块的左右大括号位置，`OptionalPunctuation` 用来允许某些行尾在 `}` 后面继续出现 `;`。

输出:
	// 输出是一个 `std::optional<Range>`。
	// 成功时返回块尾 hint 应该附着的 LSP 范围；失败时返回空，意味着这个块尾不该显示提示。

伪代码:
	function computeBlockEndHintRange(BraceRange, OptionalPunctuation) {
	  begin = get file location of left brace
	  end = get file location of right brace

	  if begin or end not in main file:
	    return empty

	  rest = text from right brace to end of line
	  if rest does not start with "}":
	    return empty

	  trailing = rest after "}" and trimmed
	  if trailing is not empty and trailing != OptionalPunctuation:
	    return empty

	  if block is too short in lines:
	    return empty

	  compute exact range covering "}" or ";" after it
	  return that range
	}

要点:
- 它先要求左右括号都在主文件里，这样才能可靠地按行计算和挂载提示。
- 它要求右大括号是这一行最后的非空白主体，或者只允许后面跟一个指定的尾随标点。
- 它会检查块的行数是否达到最小限制，避免像 `class X {};` 这种过短块也显示提示。
- 它返回的是“该挂在哪一段源码上”的范围，而不是 hint 文本本身，所以它和 `addBlockEndHint` 构成前后两层：先判定落点，再包装输出。
- 对 CSS hinter 来说，这种判定器特别重要，因为块级、规则级、声明级提示都需要先确认它们是否真的有稳定的视觉落点。

24. 动机 设计目标 与 优秀代码参考

职责:
	// 这一层把我们前面得到的理解收束起来：不仅说明“为什么要做”，也说明“要做到什么程度”，并且明确“可以参考哪些成熟实现”。

依赖:

	// 还依赖我们对 CSS 调试方式的观察：目前很多语义要到浏览器 F12 里一层层确认，编辑器侧缺少前移的语义提示。

输入:
	// 输入是已经归纳出的工程问题：如何把调试中常见的确认动作前移到编辑期，如何减少噪音，如何让提示落点稳定，如何让多种 hint 共享同一套输出框架。

输出:
	// 输出是一组可直接指导 CSS hinter 设计的原则，以及一组值得对照实现的 clangd 代码模式。

伪代码:
	function summarizeLessons(clangdPatterns, cssNeeds) {
	  motivation = move debugging knowledge from browser/runtime to editor/time-of-write
	  goals = [accurate, stable, low-noise, extensible, layered]
	  references = extract reusable patterns from clangd code
	  return motivation + goals + references
	}

要点:
- 动机层：CSS 现在很多问题要在浏览器里 F12 一层层查，而 clangd 展示了如何把这类信息前移到编辑器里。
- 设计目标：不是做“另一个 DevTools 面板”，而是做“写的时候就能看到的语义提示”，帮助作者减少切换上下文。
- 优秀思想 1：`VisitCallExpr` 先做入口过滤，再把不同调用形式统一成 `Callee + Args`，说明“统一语义入口”比“在每个分支里硬写规则”更稳。
- 优秀思想 2：`processCall` 把低价值场景屏蔽、参数名选择、引用语义判断、默认参数收集放在同一条管线里，说明真正成熟的 hinter 要有清晰的候选筛选链。
- 优秀思想 3：`shouldHintName` / `shouldHintReference` 体现了“先判断信息增量是否足够，再决定是否显示”的去噪哲学。
- 优秀思想 4：`getHintRange` / `addInlayHint` 把“语义范围”与“编辑器落点”分开，说明落点合法化应该是独立的一层，而不是散落在各个业务规则里。
- 优秀思想 5：`addTypeHint`、`addBlockEndHint`、`addDesignatorHint` 说明同一输出框架可以服务不同 hint 类型，但每种类型都要有自己的专用出口和展示风格。
- 优秀思想 6：`computeBlockEndHintRange` 展示了块级提示如何在主文件、行尾、长度限制、尾随标点等条件下保持视觉稳定，这对 CSS 规则块/声明块提示非常有借鉴意义。
- 优秀思想 7：`VisitVarDecl` 和 `getOnlyParamInstantiation` 说明成熟实现不会只看表层声明，而会尽量回填到更有用的实例化语义，但又不会过度猜测。

可直接借鉴到 CSS hinter 的代码原则:
- 先统一入口，再分发语义分支。
- 先做候选筛选，再做文本拼装。
- 先做落点合法性，再做最终输出。
- 先抑制重复与噪音，再考虑覆盖率。
- 让不同 hint 类型共享一套输出框架，但保留各自的专用出口。

建议的参考顺序:
- 第一步看 `VisitCallExpr`，学统一入口和归一化。
- 第二步看 `processCall`，学候选筛选、名字选择、引用判断、默认值收集。
- 第三步看 `addTypeHint`、`addBlockEndHint`、`addDesignatorHint`，学不同 hint 类型如何共用输出层。
- 第四步看 `getHintRange`、`computeBlockEndHintRange`，学如何让提示落点稳定且不吵。
- 第五步看 `VisitVarDecl`，学如何把一类语义拆成多个子场景并统一输出。

26. 总体架构设计

职责:
	// 这一层描述我们自己的 hinter 应该如何分层。
	// 目标是让语义判断、位置计算、结果输出彼此解耦，并且每层都能单独测试。

依赖:
	// 依赖 CSS PSI、文档模型、范围模型、hint 数据结构、配置系统和测试夹具。

输入:
	// 输入是当前文档、光标或请求范围、以及与 CSS 语义相关的局部上下文。

输出:
	// 输出是标准化的 hint 列表，外加可追踪、可回归、可扩展的内部结构。

伪代码:
	function cssHintPipeline(document, range, config) {
	  snapshot = acquireDocumentSnapshot(document)
	  ast = parseCssPsi(snapshot)
	  candidates = collectSemanticCandidates(ast, range)
	  filtered = filterAndNormalize(candidates, config)
	  placements = resolveHintPlacements(filtered, snapshot)
	  hints = renderHints(placements)
	  return dedupeAndSort(hints)
	}

分层建议:
	1. 输入层: 文档快照、请求范围、配置、编辑器状态。
	2. 语义层: 从 CSS PSI 中提取候选对象，识别属性、值、嵌套、引用、覆盖、默认值。
	3. 判定层: 决定哪些候选值得提示，哪些要抑制，哪些要合并。
	4. 落点层: 决定 hint 应该贴在左侧、右侧、行尾还是块尾。
	5. 输出层: 统一构造 hint，处理排序、去重、长度限制和样式。
	6. 配置层: 控制开关、阈值、hint 类型和实验性功能。

要点:
- 语义层不要直接写 UI 逻辑。
- 输出层不要反推复杂语义。
- 判定层要集中处理噪音、重复和低价值信息。
- 落点层要独立出来，因为位置稳定性是 hint 成败的关键。
- 配置层要足够细，便于逐步放量和灰度验证。

关键考虑:
- 语义优先于表现: 先想清楚提示代表什么，再决定怎么显示。
- 稳定优先于完整: 位置不稳的提示宁可不发，也不要强行发。
- 去噪优先于覆盖: 能从源码直接看出来的内容就尽量不重复提示。
- 可扩展优先于一次做完: 先建立统一管线，再逐步加新的 hint 类型。
- 测试优先于猜测: 每一种 hint 行为都应该能用 fixture 回归验证。
- CSS 特性优先级要明确: property/value/shorthand/override/default/reference 不能混成一锅。
- 左右侧和块尾是不同语义槽位: 不要把所有提示都塞进同一种布局。

推荐的落地顺序:
1. 先做一个最小 hint 类型，验证整体管线。
2. 再做 CSS property/value 相关的核心语义。
3. 然后补 shorthand、继承、覆盖、默认值等更复杂的情况。
4. 最后再做更细的排版优化和提示风格统一。

要点:
- 设计阶段最重要的是把边界说清楚。
- 只要边界清楚，后续实现就容易拆分、调试和扩展。
- 这套考虑应该直接反映到代码目录、模块划分和测试用例组织里。

可借鉴点:

- 这个库没有 inlay hint 专用 API，所以必须自己建立“候选收集 -> 去噪 -> 落点 -> 输出”的链路。
- 它目前更偏 completion / hover / navigation，不擅长表达“编辑器内联显示”的布局策略。

- 解析器和节点模型可以直接借鉴它的分层思路，但不用照搬具体语法实现。

- completion/hover 的上下文采集方式可以变成 hinter 的候选定位方式。
- 需要增加一个专门的 inlay hint 服务入口，而不是在 completion/hover 里硬塞逻辑。
