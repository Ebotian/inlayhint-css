测试设计

目标:
- 先把测试文件名、职责和目录结构定下来，再开始写实现。
- 测试优先围绕 CSS inlay hint 的最小闭环、语义边界和落点稳定性展开。
- 参考 clangd 的测试方式：注释标记、fixture、按 hint 类型分组、先锁边界再扩展。

1. 主测试文件规划

第一批必须创建的文件:
- [src/test/css/inlayHints.test.ts](../src/test/css/inlayHints.test.ts)
- [src/test/scss/inlayHints.test.ts](../src/test/scss/inlayHints.test.ts)
- [src/test/less/inlayHints.test.ts](../src/test/less/inlayHints.test.ts)

职责划分:
- [src/test/css/inlayHints.test.ts](../src/test/css/inlayHints.test.ts)
	- 测 CSS 主线行为。
	- 覆盖 property / value / shorthand / 选择器 / at-rule / 块尾等核心场景。
- [src/test/scss/inlayHints.test.ts](../src/test/scss/inlayHints.test.ts)
	- 测 SCSS 的变量、嵌套、mixin、参数转发等扩展语义。
- [src/test/less/inlayHints.test.ts](../src/test/less/inlayHints.test.ts)
	- 测 LESS 的变量、mixin、参数转发和派生语义。

命名原则:
- 文件名统一用 `inlayHints.test.ts`，这样和 `hover.test.ts`、`completion.test.ts` 的风格一致。
- 语言差异通过目录区分，不在文件名里额外加前缀。
- 每个文件只关注一种语言族，避免把 CSS / SCSS / LESS 混到一个测试文件里。

2. 测试辅助文件规划

建议新增的辅助文件:
- [src/test/testUtil/inlayHint.ts](../src/test/testUtil/inlayHint.ts)
- [src/test/testUtil/inlayHintAssertions.ts](../src/test/testUtil/inlayHintAssertions.ts)

职责划分:
- [src/test/testUtil/inlayHint.ts](../src/test/testUtil/inlayHint.ts)
	- 负责构造 `TextDocument`、解析 AST、调用 inlay hint 接口、收集结果。
	- 负责解析注释标记，比如光标位置、期望范围、期望 hint 区域。
- [src/test/testUtil/inlayHintAssertions.ts](../src/test/testUtil/inlayHintAssertions.ts)
	- 负责统一断言 hint 的 label、kind、range、padding 和排序结果。
	- 负责按 hint 类型过滤后再断言，避免测试代码重复。

为什么要拆出来:
- 主测试文件会大量重复“准备文档 -> 解析 -> 调接口 -> 断言”流程。
- 单独抽辅助文件，后面新增 CSS hint 类型时只要补数据，不用复制整套测试流程。

3. fixture 目录规划

如果需要跨文件或大场景测试，再增加 fixture:
- [test/inlayHintFixtures/css/](../test/inlayHintFixtures/css/)
- [test/inlayHintFixtures/scss/](../test/inlayHintFixtures/scss/)
- [test/inlayHintFixtures/less/](../test/inlayHintFixtures/less/)

建议放进去的场景:
- 跨文件引用。
- `@import` / `@use` / `@forward` 相关路径。
- 大文件或多块规则的稳定性测试。
- 需要多个文件联动才能验证的语义链。

不建议一开始就放 fixture 的场景:
- 单个 declaration 的局部提示。
- 单个 selector / 单个 value 的局部抑制规则。
- 任何可以直接用内联字符串覆盖的场景。

4. 第一阶段测试清单

建议优先写的用例，按文件分配:

在 [src/test/css/inlayHints.test.ts](../src/test/css/inlayHints.test.ts) 里先写:
- 最小 property/value hint。
- shorthand 分量 hint。
- 左侧 / 右侧 hint 的基础落点。
- 低价值信息抑制。
- 重复 hint 去重。
- 块尾 hint 的最小场景。
- 配置开关开启/关闭。

在 [src/test/scss/inlayHints.test.ts](../src/test/scss/inlayHints.test.ts) 里先写:
- 变量引用提示。
- mixin 参数提示。
- 嵌套规则中的语义定位。
- 参数转发链提示。

在 [src/test/less/inlayHints.test.ts](../src/test/less/inlayHints.test.ts) 里先写:
- 变量提示。
- mixin 调用提示。
- guard / nested rule 的简单语义。

5. 测试层级设计

第 1 层: 单元级
- 对一个 AST 节点或一个语义规则做最小输入输出验证。
- 优先写在主测试文件里。

第 2 层: 语义级
- 验证 property / value / reference / override / default 等语义链。
- 验证哪些信息应该显示，哪些应该抑制。

第 3 层: 落点级
- 验证 hint 应该挂在左侧、右侧、行尾还是块尾。
- 验证范围在不同结构里是否稳定。

第 4 层: 集成级
- 验证配置、去重、排序、跨文件引用、大文件稳定性。
- 如果需要跨文件，放到 fixture 目录里。

6. 命名风格

测试函数命名:
- 用 `suite('CSS Inlay Hints', ...)` 作为总套件。
- 子用例按语义分组：`property hints`、`shorthand hints`、`block end hints`、`scss variables`、`less mixins`。

fixture 命名:
- 用语义名，不用实现名。
- 例如 `property-basic.css`、`shorthand-override.css`、`block-end-min-line.css`、`scss-forwarding.scss`。

断言命名:
- 统一按 `expectedHint`、`expectedRange`、`expectedKind`、`expectedLabel` 这类结构命名。
- 不要让每个测试自己发明一套断言字段。

7. TDD 顺序

建议的写法顺序:
1. 先写 [src/test/css/inlayHints.test.ts](../src/test/css/inlayHints.test.ts) 的最小失败用例。
2. 再补 [src/test/testUtil/inlayHint.ts](../src/test/testUtil/inlayHint.ts) 的公共测试工具。
3. 然后写对应的实现代码。
4. 通过后再扩展到 SCSS / LESS。
5. 最后再补 fixture 目录和跨文件场景。

8. 需要特别补的测试点

- CSS 选择器和属性值的语义边界。
- shorthand 展开后的分量提示。
- 显式写出的内容不重复提示。
- 重复候选的去重。
- 块尾提示的落点稳定性。
- 配置开关关闭时的完全静默。
- 大文件场景下的性能和稳定性。

结论:
- 第一批真正要创建的主文件，就是 `src/test/css/inlayHints.test.ts`、`src/test/scss/inlayHints.test.ts`、`src/test/less/inlayHints.test.ts`。
- 如果公共测试流程重复太多，就抽 `src/test/testUtil/inlayHint.ts` 和 `src/test/testUtil/inlayHintAssertions.ts`。
- 只有跨文件和大场景，才考虑加 `test/inlayHintFixtures/...`。
