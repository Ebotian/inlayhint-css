开发计划

目标:
- 为 CSS 实现一个通用的 inlay hint 系统，优先支持“内联形参名式”的提示体验。
- 参考 clangd 的工程分层方式，以及 vscode-css-languageservice 的 CSS 解析与语义服务结构。
- 先建立稳定可工作的最小闭环，再逐步扩展到更复杂的 CSS 语义场景。

1. 范围定义

职责:
- 先冻结第一版要做的 hint 类型，避免一开始把所有 CSS 语义都塞进去。

建议范围:
- CSS property value 的语义提示。
- shorthand 展开后的分量提示。
- 引用、继承、覆盖、默认值等与结果来源有关的提示。
- 后续再考虑 LESS / SCSS 的变量、mixin、参数转发等扩展场景。

不做范围:
- 不先追求全量 CSS 规则覆盖。
- 不直接做浏览器 DevTools 的替代品。
- 不把 completion / hover 的逻辑硬塞进 inlay hint。

2. 总体架构

分层:
1. 输入层
	- 接收文档快照、请求范围、配置和编辑器能力。
2. 语义层
	- 从 CSS AST / PSI 中提取候选语义。
3. 判定层
	- 决定哪些候选值得显示，哪些应抑制。
4. 落点层
	- 计算 hint 该显示在左侧、右侧、行尾或块尾。
5. 输出层
	- 统一生成 hint，处理去重、排序、长度限制和样式。
6. 配置层
	- 控制启用开关、实验性能力和不同 hint 类型的阈值。

核心原则:
- 语义判断和展示位置分离。
- 候选筛选和结果输出分离。
- 稳定性优先于覆盖率。
- 去噪优先于强行显示。

3. 第一阶段实现路线

阶段 1: 最小闭环
- 目标是打通“读取文档 -> 解析 -> 采集候选 -> 生成 hint -> 展示结果”。
- 先实现一个最简单的 hint 类型，用来验证整体管线。

阶段 2: 语义采集
- 接入 CSS 解析结果，梳理哪些节点可以作为 hint 候选。
- 利用 node path、offset、range 这些基础能力定位语义。
- 建立元数据层，统一存放属性、值限制、描述信息和来源信息。

阶段 3: 位置与输出
- 把“提示文本怎么生成”与“提示挂在哪里”拆开。
- 为左侧 hint、右侧 hint、块尾 hint 设计不同的落点策略。
- 加入长度限制和可见性判断，避免产生噪音。

阶段 4: 去噪与整理
- 对重复候选做合并。
- 对明显可从源码直接看出的信息做抑制。
- 对输出做排序和稳定化。

阶段 5: 测试固化
- 用 fixture 方式锁定行为。
- 为每一种 hint 类型准备回归测试。
- 对边界情况单独补测试，避免回归时难以判断是语义问题还是落点问题。

阶段 6: 扩展能力
- 再增加更多 CSS 场景。
- 按需扩展到 LESS / SCSS。
- 逐步增加复杂语义：继承链、覆盖链、默认值链、转发链。

4. 架构设计考虑

需要提前回答的问题:
- 什么信息值得显示。
- 什么信息已经由源码显式表达，不需要重复提示。
- 提示应该挂在什么位置才稳定自然。
- 哪些 hint 类型应该共享同一套输出框架。
- 哪些 hint 类型需要独立的专用出口。

设计约束:
- 位置不稳的提示宁可不发。
- 低价值信息宁可不发。
- 共享的能力放到公共层。
- 语义差异大的内容单独开分支。
- 每一层都要可测试、可替换、可扩展。

5. 借鉴来源

clangd 提供的启发:
- 先统一入口，再分发规则。
- 先做语义归一，再做候选判断。
- 先算可落点，再生成最终 hint。
- 一个调用点可以同时产生多种 hint，但每种 hint 都要有自己的出口。

vscode-css-languageservice 提供的启发:
- facade 层只负责组装服务。
- completion / hover 都是“位置 -> node path -> 语义判断”的模式。
- `cssNodes.ts` 提供了稳定的 offset / length / path 基础。
- `dataManager.ts` 提供了统一的元数据管理方式。

6. 我们自己的实现目标

短期目标:
- 做出一个最小可用的 CSS inlay hint 原型。
- 能在编辑器里稳定显示。
- 能通过测试验证。

中期目标:
- 覆盖更多 CSS 语义场景。
- 提供可配置的 hint 开关。
- 建立稳定的去噪和排序策略。

长期目标:
- 把常见的 CSS 语义确认动作前移到编辑期。
- 减少用户频繁切换到浏览器 DevTools 的成本。
- 让 hint 成为 CSS 编写过程中的常驻语义辅助，而不是临时调试工具。

6.1 显示设计

目标:
- 把“算出 hint”和“显示出来”明确拆开，避免把渲染逻辑混进语义逻辑。
- 让 CSS inlay hint 能通过 VS Code 的语言特性管线稳定展示。

显示链路:
1. 语言服务层
	- `cssLanguageService.ts` 只负责暴露 `doInlayHints`。
	- `cssInlayHints.ts` 只负责从 stylesheet 计算 hint 数据。
2. provider 层
	- 由外层消费方注册 `vscode.languages.registerInlayHintsProvider(...)`。
	- provider 只做文档到语言服务的转发，不承载业务语义。
3. 编辑器层
	- 由 VS Code 的 inlay hint controller 负责真正绘制、缓存和刷新。
	- 显示位置、折叠、滚动、重绘都服从编辑器已有机制，不在本库重复实现。

显示原则:
- 位置稳定优先，位置不稳就不显示。
- 低价值提示优先抑制，宁可少发也不要乱发。
- 同一类 hint 的样式要一致，避免让用户记忆多个视觉规则。
- 以“补充信息”为主，不抢源码本身的可读性。

显示策略:
- 左侧 / 右侧 / 行尾 / 块尾要有明确语义边界。
- shorthand 类提示优先放在值附近，避免跨行跳跃。
- 复杂 hint 可以先隐藏，等有稳定语义后再开放。
- 超长 label 需要截断或降级，避免占用过多编辑区域。

刷新与交互:
- 文档变化后应重新计算可见范围内的 hint。
- 配置变化后应触发 provider 刷新。
- 如果未来支持可点击或可展开 hint，再单独补 resolve 路径。

与测试的对应关系:
- 为 display 设计单独补一组 fixture，验证 hint 是否出现在正确位置。
- 需要测试不同缩放、换行、长行、折叠和请求范围下的可见性。
- 需要测试 hint 的排序、重叠和去重是否在编辑器里保持稳定。

7. 推荐下一步

1. 先定义第一版 hint 类型和不做清单。
2. 再定模块划分：解析、语义、落点、输出、测试。
3. 然后开始写最小原型。
4. 最后补测试和边界规则。

8. 测试与 TDD 方案

目标:
- 用测试先定义行为，再写实现。
- 把 hint 的语义、落点、去噪和配置行为都固定下来，避免后面扩展时回归。

clangd 可借鉴的测试方式:
- 用带标记的源码片段表达光标位置和期望范围。
- 按 hint 类型分组测试，而不是把所有场景混在一起。
- 用 fixture 覆盖边界条件、抑制条件和配置开关。
- 先写小而精的场景，再补大而复杂的场景。

我们自己的测试分层:
1. 解析层测试
	- 确认 CSS 文本能被解析成稳定的节点树。
	- 覆盖 declaration、selector、rule block、at-rule、nested rule 等基础结构。
2. 语义层测试
	- 确认候选提取是否正确。
	- 验证 property / value / shorthand / reference / default / override 这些语义链。
3. 落点层测试
	- 确认 hint 位置是否稳定。
	- 覆盖左侧、右侧、行尾、块尾的不同位置策略。
4. 输出层测试
	- 确认 label 拼装、长度限制、排序和去重。
	- 验证低价值信息是否被抑制。
5. 配置层测试
	- 确认不同开关对输出的影响。
	- 验证启用 / 关闭 / 阈值变化时的行为。

推荐的 fixture 风格:
- 用标记语法描述目标位置和期望范围。
- 一个 fixture 只验证一个核心行为。
- 复杂场景拆成多个小 fixture，而不是塞进一个大文件。
- 对边界案例单独命名，方便后续回归。

建议的测试顺序:
1. 先测最小闭环：一个 hint 能被正确生成和显示。
2. 再测抑制条件：已经显式写出的信息不重复显示。
3. 再测落点稳定性：同一语义在不同结构中是否挂在正确位置。
4. 再测去噪：重复、过长、低价值场景是否被过滤。
5. 最后测扩展场景：shorthand、继承、覆盖、转发、复杂嵌套。

TDD 规则:
- 先写失败测试，再补实现。
- 每次只推进一个语义点，避免一次改太多。
- 实现完成后立刻补回归测试。
- 任何新 hint 类型都必须先有 fixture，再有代码。

我们要特别补的测试:
- CSS 自己没有 clangd 那种参数提示和块尾提示现成语义，所以要额外验证 property/value 以及 shorthand 分量的提示。
- 要补 CSS 选择器、@media、@supports、@keyframes 这类块级语义的提示测试。
- 要补浏览器/规范元数据驱动的提示测试，确认 dataManager 的内容真的能进入 hint。
- 要补性能边界测试，避免大文件下 hint 生成过慢。

结论:
- clangd 的测试最值得学的是“用测试定义语义边界”。
- 我们的 TDD 重点不是模仿它的 C++ 场景，而是借它的方法，把 CSS hint 的规则、位置和噪音控制先写成可执行的 fixture。

- 新增实现文件 1 个。
- 新增测试文件 1 个。

- 改动范围小。
- 回归风险低。
- 方便按 TDD 一步步推进。
- 后续扩展到 SCSS / LESS 时可以复制同样的模式。
